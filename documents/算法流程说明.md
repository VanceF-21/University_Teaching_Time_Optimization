# 课表重排算法流程说明文档

> **项目背景**：本项目针对英国某大学的课表调整需求，研究能否将核心教学时间压缩至 9:00–17:00（场景 S1）或取消周五 12:00 后课程（场景 S2），同时尽量减少学生课程冲突。为此，系统采用两类互补的算法：**混合整数规划（MIP）精确模型** 与 **启发式算法（贪心 + 局部搜索）**。

## 1. 问题定义与共同基础

### 1.1 核心任务

将所有**被移位事件**（即在当前时间窗口之外的课程，主要为整班讲座 WholeClass Lecture）重新分配至合法时间槽，使学生级别的课程冲突最小化。

### 1.2 关键概念

| 术语 | 说明 |
|------|------|
| **被移位事件** $E_{disp}$ | 当前排在允许时窗外、需要重新安排的事件集合（主要取整班讲座） |
| **固定事件** $E_{fixed}$ | 已处于允许时窗内、时间槽不变的事件 |
| **合法时间槽** $T_e$ | 事件 $e$ 可被安排的（星期, 开始小时）对列表 |
| **冲突对** $C$ | 至少共享一名学生的两个事件构成的对 $(e_1, e_2)$ |
| **共享学生数** $w(e_1,e_2)$ | 冲突对的权重，反映冲突的严重程度 |

### 1.3 时间槽合法性规则

```
合法开始小时：9, 10, 11, ..., 17（整点）
结束限制：
  S1（全天压缩至9–17）：结束时间 ≤ 17:00
  S2（取消周五下午）  ：结束时间 ≤ 18:00，且周五课程结束时间 ≤ 12:00
```

## 2. 算法一：混合整数规划（MIP）模型

MIP 模型追求**全局最优解**，借助 FICO Xpress 商业求解器在给定时间内找到理论上最优的课程安排。

### 2.1 决策变量

$$x_{e,t} \in \{0, 1\}$$

表示事件 $e \in E_{disp}$ 是否被分配到时间槽 $t \in T_e$（1 = 分配，0 = 不分配）。

$$z_{e_1,e_2} \in \{0, 1\}$$

表示冲突对 $(e_1, e_2)$ 在重排后是否仍然发生冲突（1 = 冲突，0 = 无冲突）。

### 2.2 约束条件

**约束①　唯一分配约束**（硬约束）

$$\sum_{t \in T_e} x_{e,t} = 1 \quad \forall\, e \in E_{disp}$$

每个被移位事件必须且只能被分配到一个合法时间槽。

---

**约束②　与固定事件的冲突避免**（硬约束）

$$x_{e,\, t_{fixed}} = 0$$

若 $e \in E_{disp}$ 与某固定事件 $e_{fixed} \in E_{fixed}$ 存在冲突，且固定事件所在时间槽 $t_{fixed}$ 也在 $e$ 的合法槽集合中，则禁止将 $e$ 安排在该槽位，避免直接冲突。

---

**约束③　被移位事件间的冲突检测**

$$x_{e_1,t} + x_{e_2,t} \leq 1 + z_{e_1,e_2} \quad \forall\,(e_1,e_2) \in C_{dd},\; \forall\, t \in T_{e_1} \cap T_{e_2}$$

若两个被移位事件同时被排在相同时间槽，则冲突指示变量 $z_{e_1,e_2} = 1$，否则可以为 0。

### 2.3 目标函数

$$\min \sum_{(e_1,e_2) \in C_{dd}} w(e_1,e_2) \cdot z_{e_1,e_2}$$

最小化所有冲突对的**加权冲突总数**，权重为两门课共享的学生人数，即优先消除影响学生最多的冲突。

### 2.4 规模限制与求解参数

由于数据规模较大（约 3.2 万个事件、93 万条学生-事件记录），MIP 模型对规模进行了限制：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `MAX_EVENTS` | 500 | 最多纳入的被移位事件数 |
| `SOLVER_TLIMIT` | 300 秒 | 求解时间上限 |
| `MIP_GAP` | 2% | 可接受的最优性间隙 |

### 2.5 MIP 模型完整流程

```
┌─────────────────────────────────────────────────────────────────┐
│                     MIP 模型执行流程                             │
└─────────────────────────────────────────────────────────────────┘

第一步：数据准备
  ├── 从预处理结果中读取事件表和冲突对表
  ├── 筛选被移位事件（E_disp），限制为整班讲座且数量 ≤ MAX_EVENTS
  └── 标记固定事件（E_fixed）

第二步：构建合法时间槽
  ├── 对每个被移位事件，根据时长和场景规则生成合法 (星期, 小时) 列表
  └── 过滤掉无任何合法槽位的事件（标记为"无法安排"）

第三步：构建决策变量
  ├── 创建二值变量 x[e, t]（分配矩阵）
  └── 创建冲突指示变量 z[e1, e2]（冲突矩阵）

第四步：添加约束
  ├── 约束①：每个事件恰好分配一个时间槽
  ├── 约束②：固定事件冲突禁令（直接将对应 x[e,t] 设为 0）
  └── 约束③：被移位事件间冲突检测（Big-M 线性化）

第五步：设置目标函数
  └── 最小化 Σ w(e1,e2)·z[e1,e2]

第六步：调用 Xpress 求解器
  ├── 设置时间上限（SOLVER_TLIMIT）
  ├── 设置相对间隙（MIP_GAP）
  └── 求解 MIP 问题

第七步：提取结果
  ├── 读取每个被移位事件的最终时间槽（x[e,t]=1 的 t）
  ├── 统计残余冲突对数量和加权冲突分数
  └── 计算午休可行性等辅助指标

第八步：输出
  ├── mip_results_{scenario}.csv   ← 每个事件的分配结果
  └── mip_summary_{scenario}.csv  ← 求解状态、冲突数、指标汇总
```

### 2.6 MIP 模型的优势与局限

**优势**
- 在给定时间内追求全局最优，结果具有理论保证（最优性间隙 ≤ 2%）
- 硬约束严格满足，不会出现明显非法安排
- 适合决策者需要可验证最优解的场景

**局限**
- 计算复杂度随事件数呈指数级增长，规模受限（当前上限 500 个事件）
- 对超出规模限制的事件无法处理，需截断

## 3. 算法二：启发式算法

启发式算法不追求全局最优，而是通过**快速近似策略**在短时间内得到质量较好的可行解，可处理全部被移位事件。系统实现了两阶段启发式：**贪心分配**（阶段一）+ **局部搜索**（阶段二）。

---

### 3.1 阶段一：贪心分配（最受约束优先）

#### 核心思想

优先处理"最难安排"的事件——即冲突邻居最多的事件，为其先抢占较优时间槽。

#### 详细步骤

```
┌──────────────────────────────────────────────────────────────────┐
│              贪心分配算法（Greedy Assignment）                     │
└──────────────────────────────────────────────────────────────────┘

输入：被移位事件集合 E_disp，冲突对列表 C，场景规则

Step 1：构建冲突邻接表
  对每个事件 e，计算其冲突邻居数量（即 degree）
  ┌───────────────────────────────┐
  │ degree(e) = |邻居集合 adj[e]| │
  └───────────────────────────────┘

Step 2：按冲突数降序排列事件
  排序：degree(e₁) ≥ degree(e₂) ≥ ... （冲突最多的先处理）

Step 3：逐个事件分配时间槽
  For 每个事件 e（按排序顺序）：
    ① 获取 e 的合法时间槽列表 T_e（按星期/小时排序）
    ② For 每个候选时间槽 t ∈ T_e：
         计算 clash_count(t) = 已分配的冲突邻居中与 t 重叠的数量
    ③ 选择 clash_count 最小的时间槽 t*
         ├── 若 clash_count(t*) = 0：无冲突分配（硬约束满足）
         └── 若 clash_count(t*) > 0：软冲突（记录惩罚值）
    ④ 记录分配结果：assignment[e] = t*

输出：初始分配方案 assignment，各事件的冲突惩罚值
```

**时间复杂度**：$O(|E_{disp}| \times |T| \times \bar{d})$，其中 $\bar{d}$ 为平均冲突邻居数，$|T|$ 为合法槽数量。

---

### 3.2 阶段二：局部搜索（单事件迁移改进）

#### 核心思想

从贪心解出发，反复尝试将某个事件移动到另一个合法时间槽，若能降低总冲突分数则接受，直至无法改进为止。

#### 详细步骤

```
┌──────────────────────────────────────────────────────────────────┐
│          局部搜索算法（Local Search / Relocation）                 │
└──────────────────────────────────────────────────────────────────┘

输入：贪心分配结果 assignment，冲突邻接表，最大迭代次数

Step 1：计算初始总冲突分数
  score = Σ_{(e1,e2)∈C，且二者分配时间槽重叠} w(e1,e2)

Step 2：迭代改进（最多 max_iterations 轮）
  While 存在改进 且 未达迭代上限：
    improved = False
    For 每个被移位事件 e1：
      current_slot = assignment[e1]
      For 每个备选时间槽 t ∈ T_{e1}，t ≠ current_slot：
        ① 临时将 e1 移动到 t：assignment[e1] = t
        ② 重新计算总冲突分数 new_score
        ③ If new_score < score：
             接受移动（首次改进策略）
             score = new_score
             improved = True
             Break（继续下一个事件）
        ④ Else：
             撤销移动：assignment[e1] = current_slot
    If improved = False：
      终止迭代（局部最优）

Step 3：记录每轮迭代的分数变化（用于绘制收敛曲线）

输出：
  - 改进后的分配方案 assignment
  - 最终总冲突分数 final_score
  - 迭代日志（每轮分数）→ heuristic_iteration_log_{scenario}.csv
```

**邻域结构**：单事件迁移（Relocation）——每次只移动一个事件，不涉及两事件间的槽互换（互换邻域复杂度更高，为 $O(|E_{disp}|^2 \times |T|)$，未采用）。

**接受策略**：首次改进（First Improvement）——找到第一个改进邻居即接受，速度快于最优改进。

**终止条件**：当一轮完整遍历后没有任何事件能通过移动降低总分时，停止迭代（局部最优）。

### 3.3 启发式算法完整流程（两阶段合并）

```
┌─────────────────────────────────────────────────────────────────┐
│                  启发式算法整体执行流程                           │
└─────────────────────────────────────────────────────────────────┘

第一步：数据准备
  ├── 读取全量被移位事件（不限 MAX_EVENTS，覆盖全部事件类型）
  ├── 构建冲突邻接表 adj（event_id → 冲突邻居集合）
  └── 构建冲突权重字典 weights（(e1,e2) → 共享学生数）

第二步：生成合法时间槽
  └── 对每个事件，按场景规则生成 T_e

第三步：贪心分配（阶段一）
  ├── 计算每个事件的冲突度（degree）
  ├── 降序排列事件
  ├── 逐个事件选择冲突最少的合法槽
  └── 记录初始分配方案及每个事件的冲突惩罚

  ↓ 贪心解质量评估
  ├── 统计零冲突分配的整班课数量及比例
  └── 计算贪心阶段加权冲突总分

第四步：局部搜索改进（阶段二）
  ├── 以贪心解为起点
  ├── 反复执行单事件迁移，接受改进移动
  └── 记录每轮迭代分数，直至局部最优

  ↓ 最终解评估
  ├── 最终加权冲突分数
  ├── 相对贪心解的改进幅度
  └── 时间槽负载均衡度（变异系数 CV）

第五步：计算辅助指标
  ├── 午休可行性：重排后有 12–14 时空闲的学生比例
  ├── 各天承接的重排事件数（负载分布）
  └── 无法安排事件数（T_e 为空的事件）

第六步：输出
  ├── heuristic_assignment_{scenario}.csv   ← 分配结果
  ├── heuristic_summary_{scenario}.csv      ← 汇总指标
  └── heuristic_iteration_log_{scenario}.csv ← 局部搜索收敛日志
```

### 3.4 启发式算法的优势与局限

**优势**
- 无规模限制，可处理全部被移位事件
- 运行速度快，无需商业求解器许可
- 两阶段设计兼顾初始解质量（贪心）和迭代改进（局部搜索）
- 提供详细收敛日志，便于分析算法行为

**局限**
- 无法保证全局最优，结果依赖初始贪心解的质量
- 局部搜索可能陷入局部最优（可通过多次随机重启缓解）
- 贪心排序策略（按冲突度）未考虑事件间的全局依赖关系

## 4. 两类算法的对比

| 维度 | MIP 精确模型 | 启发式算法（贪心 + 局部搜索） |
|------|-------------|------------------------------|
| **求解质量** | 接近全局最优（间隙 ≤ 2%） | 局部最优，质量依赖启发策略 |
| **规模适用性** | 限于前 500 个事件（整班课） | 全量事件，无上限 |
| **运行时间** | ≤ 300 秒（设定上限） | 秒级至分钟级，远快于 MIP |
| **依赖工具** | FICO Xpress 商业求解器 | 纯 Python，无额外依赖 |
| **约束处理** | 硬约束严格满足，软约束目标化 | 硬约束尽力满足，软约束记为惩罚 |
| **可解释性** | 数学模型明确，结果可验证 | 流程直观，收敛曲线可视化 |
| **适用场景** | 需要最优保证的小规模子问题 | 快速评估大规模可行解 |

### 互补关系

两类算法在本项目中相互补充：

- **MIP 模型**聚焦于最重要的整班讲座（影响学生最广），在严格约束下求得高质量解，为决策提供理论依据。
- **启发式算法**覆盖全量事件，快速生成完整的可行排课方案，并通过局部搜索持续改进，作为 MIP 无法覆盖部分的补充。
